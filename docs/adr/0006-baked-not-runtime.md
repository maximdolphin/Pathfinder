# ADR-0006 — Generated offline into assets; runtime generation only where nothing else works

**Status:** Accepted
**Date:** 2026-09-09
**Related:** ADR-0005, `docs/architecture/module-map.md`

## Context

Everything in this project is built at runtime, and that was never decided — it
is what the prototype did to answer a rendering question in a hurry, and it has
been the architecture ever since. Checked rather than remembered, on
2026-09-09:

- There is **no level**. The project loads `/Engine/Maps/Entry`, an empty engine
  map. There are no `.umap` files.
- There are **no project assets** except the sixty-nine surface textures
  imported the day before this was written.
- **Every material is `RF_Transient`**, constructed as a node graph in C++ on
  each launch, inside `#if WITH_EDITOR`.
- **All geometry is `UProceduralMeshComponent`**, generated on the game thread.

What that costs, in order of severity:

**A packaged build has no materials.** `LedgerSurfaceCooked.cpp` returns
`nullptr` for every one of them, by design, with a comment calling it a known
hole. It is a known hole that means there is no game outside the editor.

**No Nanite, anywhere.** Procedural mesh components cannot use it. That is one
of the two or three largest visual and performance wins the engine offers, and
it is currently unavailable to every object in the world.

**No mesh distance fields.** This already cost something concrete: Lumen had to
be forced onto hardware ray tracing, because its software path traces against
distance fields and nothing here has any.

**Generation is on the game thread**, which is where the frame budget is
failing — 20 to 31 ms through every low-altitude phase, against a 16.7 ms
budget, with the GPU at 5 to 9.

## Decision

**Content is generated offline into real Unreal assets. Runtime generation is
reserved for the one thing that cannot be an asset.**

Three tiers, and the line between them is whether the thing can exist before
the game runs:

**1. Baked.** Ships, buildings, props, rocks, vegetation, and every material.
Produced by a generator run as an editor commandlet, saved as `.uasset`, and
loaded at runtime like any other asset. They get Nanite, automatic LODs,
distance fields, GPU instancing, streaming and cooking — none of which is work
we have to do, and all of which is unavailable to a runtime mesh.

**2. Streamed.** Planetary terrain, and only that. A 6,371 km planet with
seamless orbit-to-surface cannot be an asset; there is no authoring step that
produces it and no disk that holds it. It stays procedural and streamed. The
*component type* it streams into is a separate question and an open one.

**3. Placed.** A real level, with the planet, the sun, the atmosphere and the
post-process volumes as actors a person can see and select, rather than as
objects a subsystem spawns into an empty engine map.

## Why this changes ADR-0005 rather than contradicting it

ADR-0005 says every asset is generated by rule because nothing is bought. That
stands. This decides **when** the rule runs: once, offline, producing an asset —
not on every launch, producing a transient object.

The distinction is not academic. It is the difference between a generated ship
that Nanite renders at film density with automatic LODs, and a generated ship
that is a procedural mesh with none of that. Same generator, same rules, same
output geometry; one is a game asset and one is a tech demo.

So the generators scheduled in M12 produce **assets**, and the eight tasks
added for them were written against the wrong target before this ADR existed.

## Why not bake the terrain too

Because it cannot be. The planet is 6,371 km in radius and rendered from orbit
to boot height with no loading screen; the deepest LOD is 4.8 m quads. Baking
that is not a large export, it is an impossible one. Star Citizen generates
theirs at runtime for the same reason.

This is the one place where runtime generation is the right answer rather than
the default one, and stating it that way is the point of this ADR: everything
else was runtime because nobody chose.

## Why not keep building materials at runtime

It is genuinely convenient — a material is code, it is in version control, it
diffs, and there is no asset to get out of step with the source. Those are real
benefits and they are why it was not noticed as a problem.

But it makes shipping impossible, it recompiles shaders on every launch, and
`#if WITH_EDITOR` around the entire look of the game is a load-bearing
`#if WITH_EDITOR`. The compromise that keeps the benefit: **the material graphs
stay in C++ and stay the source of truth, and a commandlet runs them once and
saves the result.** The code is still what a diff shows; the asset is what the
game loads. Same arrangement the surface textures already use — a generator, a
manifest, a validator, and a real asset at the end.

## Consequences

- A new milestone before the planetary work, because the packaged-build hole
  and the Nanite exclusion get more expensive with every asset added on top.
- `LedgerSurfaceCooked.cpp` stops being a file full of `nullptr` and becomes a
  loader.
- The M12 generator tasks output `.uasset`; their acceptance criteria change.
- The terrain component type becomes a measured question rather than an
  assumption, since it is now the only runtime-generated geometry left and it
  owns the game-thread cost.
- A packaged build that runs the flight becomes a gate, not an aspiration.
