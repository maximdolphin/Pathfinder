# Which component the terrain is made of, measured (T423)

`UProceduralMeshComponent` was the prototype's choice. It was never compared
against anything, which makes it a default that survived rather than a
decision. This is the comparison.

Every number here is a mean or a percentile over one phase of the same
scripted flight — 160 seconds, eleven phases, same seed, same machine, nothing
else running. The raw reports are in `terrain-component/`, one file per run.

Run it either way:

```bash
UnrealEditor.exe client/Ledger.uproject -game -terraincomponent=static
```

## First: the measurement that mattered was not the component

The frame budget has failed on the **game thread** for the whole project: 20 to
33 ms at low altitude against 16.7, with the GPU idle at 5 to 9. The only
terrain cost anybody had a number for was upload, which worsts at about 7 ms,
and `FLedgerTerrainStats::LastFrameUploadMs` carried a comment saying upload
"is now the *only* terrain cost on the game thread". Nothing had ever measured
that claim.

So before comparing components, `ALedgerPlanet::Tick` was broken into its
phases. The first run said:

```
tick ms (worst)  tree 24.07  harvest 7.03  collect 0.50  sort 6.45  imbalance 1.15  whole 31.87
```

and later, in the frame where a climb collapses the tree,

```
tick ms (worst)  tree 380.22  harvest 11.48  collect 2.72  sort 7.53  imbalance 2.06  whole 381.28
```

`tree` is `UpdateTree`, the LOD walk. Not upload. Upload was third. The
standing suspicion had been the per-frame imbalance diagnostic, which costs 1
to 2 ms.

Terrain against the whole game thread, before any change:

| phase | game ms | terrain ms | terrain share |
|---|---|---|---|
| atmospheric entry | 9.9 | 5.1 | 52% |
| surface | 20.8 | 12.8 | 62% |
| town | 20.7 | 12.9 | 62% |
| ridge sweep | 33.4 | 18.8 | 56% |
| coast | 26.7 | 11.7 | 44% |
| underwater | 25.9 | 17.1 | 66% |

### Why the tree walk cost 24 ms

`UpdateTree` needs the distance to the **ground**, not to the reference sphere —
at low altitude over a mountain that difference is the entire LOD decision. It
got it by calling `SurfaceRadiusAt`, a full fractal elevation sample, once per
visited node per frame. A node's centre never moves, so that sample has the
same answer for the life of the node.

Caching it on the node (`FLedgerQuadNode::SurfacePoint`, set in `Split`) is
five lines:

| phase | terrain ms before | after |
|---|---|---|
| atmospheric entry | 5.14 | 2.13 |
| surface | 12.83 | 8.33 |
| town | 12.87 | 8.25 |
| ridge sweep | 18.83 | 11.21 |
| coast | 11.70 | 4.25 |
| underwater | 17.10 | 5.89 |

Flight p99 43.3 ms → 35.1 ms. Still failing the budget, but the largest single
item in the terrain tick is gone.

## The component comparison

Both backends live behind one seam, `LedgerPatchComponents.h`, and the
streaming code is identical up to the upload call. The candidates:

**Procedural** — `UProceduralMeshComponent::CreateMeshSection`, interleaved
buffers straight into a render resource, async collision cook.

**Static** — a `UStaticMeshComponent` whose `UStaticMesh` is built per patch by
`BuildFromMeshDescriptions`. Chosen as the alternative because everything the
rest of M2W gained by baking — Nanite, LODs, distance fields, the ordinary
renderer's culling — is available to a static mesh component and to nothing
else.

### Throughput is the whole story

Both runs below are from the same build, back to back, on an idle machine:
`05-procedural-control.txt` and `04-static.txt`.

|  | procedural | static |
|---|---|---|
| patches uploaded over the flight | 121,918 | 8,212 |
| uploads per second | 762 | 51 |
| worst upload frame (game thread) | 14.8 ms | 41.6 ms |
| typical upload frame at low altitude | under 1 ms | 12 to 24 ms |
| patch cache reuse | 81% | none possible |
| **worst hole count** | **6** | **2,584** |
| visible leaves / deepest depth, late flight | 388 / 5 | 247 / 4 |
| flight p99 | 33.1 ms | 29.0 ms |

Fifteen times the throughput at a third of the worst-frame cost, and that is
the whole comparison. The 6 ms upload budget is a budget for the procedural
backend and a joke for the static one: a single `BuildFromMeshDescriptions`
overruns it, so the loop uploads one patch and leaves, every frame, forever.

**The static run's p99 is lower, and it means nothing.** 2,584 holes against 6
is a starved world: fewer patches, a shallower tree, less to draw. It is faster
in the way that not drawing the terrain is faster. `compare_captures.py`
between the two runs' images puts the worst single channel difference at 199
against a regression limit of 16, and the coast frame at a mean of 92. The
images are in `terrain-component/procedural-captures/` and
`terrain-component/static-captures/`; the town frame is the clearest of them.

### Three things the static backend cannot do at runtime

1. **No cache.** `FLedgerCachedPatch` holds the procedural component's own
   `FProcMeshSection`; taking a copy on release is one memcpy and putting it
   back is `SetProcMeshSection`. A static mesh's render data is built once and
   cannot be handed back, so every patch is regenerated. That is where the
   81% reuse figure goes.
2. **No collision.** Chaos cooks collision offline. A mesh built this frame has
   nothing to cook from, so the static pool runs with collision disabled.
3. **No Nanite and no LODs.** `bFastBuild` is the only build available outside
   the editor, and it skips the pipeline that produces both — so the one
   argument for choosing a static mesh here does not survive contact with the
   runtime.

## Decision: keep `UProceduralMeshComponent`

Not because it is fast — because it is the only one of the two that can accept
geometry at the rate a streaming planet produces it, and because the three
things a static mesh was supposed to bring are all products of an offline build
that a runtime-generated patch never gets.

The seam stays. It costs one enum test in a path that already spends
milliseconds, and the next person to ask this question gets to answer it in an
afternoon instead of a week.

### What this measurement found that is still open

- **The ascent spike, ~300 ms in one frame.** Measured: it is inside the `tree`
  phase, it survived the elevation cache unchanged, and it lands in the frame
  where a climb collapses the tree. Not measured, and therefore still a
  hypothesis: that it is `Collapse` → `ReleaseSection` copying a ~1.1 MB
  `FProcMeshSection` into the cache thousands of times in that one frame. A
  timer inside `ReleaseSection` would settle it and has not been added.
- **`Leaves.Sort` worsts at 6.8 ms.** ~1,700 pointers should not cost that.
- Terrain is still 60 to 90% of the game thread at low altitude.

## A note on how two of these were found

The static backend's first two runs drew water and no land at all. Both causes
were assumptions written as fact:

- Polygon groups were created with no material slot name, on the assumption
  that group order becomes section order.
- The triangle winding was reversed, with a confident comment explaining that
  MeshDescription's front face is the opposite of the procedural component's.
  That was invented, not checked. The land was backface-culled; the water,
  seen edge-on over open ocean, was not obviously wrong, so the frame looked
  like a plausible seascape rather than like a bug.

The second one had already produced a full set of frame-time numbers before
anybody looked at the picture. Those numbers are kept in
`terrain-component/04-static-land-missing.txt` as a reminder that a report with
a VERDICT line in it is not evidence that the thing being measured was running.
